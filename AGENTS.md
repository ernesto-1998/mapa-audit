# AGENTS.md

Operating guide for AI coding agents (e.g. Codex) working in this repository.

This file defines the rules, boundaries, and conventions you must follow. The
**architecture and design decisions in this project are owned by a human
architect.** Your role is **implementation**: writing code that faithfully
realizes an already-decided design. When in doubt, implement conservatively and
flag the question — do not invent architectural decisions.

---

## 0. Hard Prohibitions (never do these)

These are absolute. Violating any of them is a critical failure.

### 0.1 Git operations — FORBIDDEN

You must **never** run, invoke, or script any Git operation. Specifically, you
must not:

- `git commit`, `git add`, or stage anything
- `git push`, `git pull`, `git fetch`, or any remote operation
- `git merge`, `git rebase`, `git reset`, `git revert`, `git cherry-pick`
- `git checkout`, `git switch`, or create/delete/rename branches
- `git stash`, `git tag`, amend history, or modify `.git/` in any way
- change Git configuration (`git config`)

You may **read** state for context only if explicitly asked (e.g. `git status`,
`git log`, `git diff`) — but you must never mutate repository history or interact
with any remote. All version-control actions are performed exclusively by the
human. Leave your changes in the working tree; do not attempt to persist them
through Git.

### 0.2 Do not change architecture or fixed contracts

The following are **fixed platform contracts** decided by the architect. You must
not alter, "improve", or work around them without explicit instruction.

**Core SDK contracts (apply everywhere):**

- **Two independent axes: adapters and transports.** Adapters capture context (per
  framework); transports deliver events (per destination). They never reference
  each other — they only talk to the core. Adding a transport must not touch any
  adapter, and adding a framework must not touch any transport.
- **The core depends only on the `Transport` interface**, never on a concrete
  transport. Do not wire RabbitMQ, a file, or any specific destination directly
  into the core. A destination is always implemented as a `Transport`.
- **Client-generated event `id`.** The event `id` (UUID) is generated by the SDK in
  `record()`, before the event reaches any transport — never by a database, never
  by the Worker. (This is harmless for console/file and essential for the queue
  transport's idempotency.) Do not change where `id` originates.
- **Fire-and-forget.** `record()` must never block the caller, never be `await`ed
  into business logic, and never throw into the host application — regardless of
  transport.
- **Nested canonical event, flattened only at output.** The event is a nested
  object (`service`, `request`, `actor`, `entity`, `payload`). Flattening to a
  tabular row is the responsibility of the transport (via the shared `flatten()`
  helper), never the core. The variable `payload` is never flattened — it stays
  JSON/JSONB.

**Queue/persistence module contracts (apply ONLY to the queue transport + Worker,
i.e. the later infrastructure module — not to the console/file SDK):**

- **Idempotency via `ON CONFLICT (occurred_at, id) DO NOTHING`.** In the Worker,
  deduplication happens at the database level, not in Worker memory. Do not replace
  this with in-memory "seen ID" tracking.
- **The Worker is the only writer to the database.** No other component issues
  writes to `audit_events`. Do not add direct DB writes elsewhere.
- **TimescaleDB hypertable** for `audit_events`, partitioned by `occurred_at`. Do
  not convert it to a plain table or change the partitioning column.
- **`dead_letter_events` is a plain table**, not a hypertable. Do not change this.
- **RabbitMQ topology** (exchanges, queues, retry/DLQ) follows the RabbitMQ + Worker
  doc exactly.

**Classification contract (applies to the event model everywhere):**

- **`event_type` = domain, `severity` = gravity, `outcome` = result.** Follow the
  classification rules in the Database Design document exactly. Do not collapse or
  reinterpret these fields.

If a task seems to require changing any of the above, **stop and ask** rather than
proceeding.

### 0.3 Other prohibitions

- Do not add new third-party dependencies without flagging them first (name the
  package, why it's needed, and a lighter alternative if one exists). Keep the base
  SDK (console/file) free of heavy dependencies — the queue transport lives in its
  own package precisely so its deps don't burden console/file consumers.
- Do not delete or rewrite existing tests to make them pass. If a test is wrong,
  flag it; don't silently remove it.
- Do not modify files under `docs/` (the design documents). Those are the
  architect's source of truth — you implement *from* them, you don't edit them.
- Do not add secrets, credentials, or connection strings to the codebase. All of
  these come from environment variables at runtime.
- Do not disable, weaken, or comment out CHECK constraints, validation, or type
  checks to make code compile or tests pass.

## 1. Your Role & Workflow

1. **Read the relevant design doc first.** Before implementing anything, consult
   the corresponding document in `docs/` (SDK Architecture, Database Design,
   RabbitMQ + Worker Architecture, etc.) and the current phase in `BUILD_PLAN.md`.
   The design is already decided; your job is to match it.
2. **Do only the assigned phase.** `BUILD_PLAN.md` is built in order; implement the
   phase you're given and no more. Do not jump ahead or combine phases.
3. **Implement in small, reviewable units.** The human reviews your work before it
   is committed.
4. **State your assumptions.** If a design doc is silent on a detail, pick the most
   conventional option, implement it, and **explicitly note** what you assumed so
   the architect can correct it in review.
5. **Flag, don't guess, on architecture.** If a task can't be done without making a
   design decision, stop and surface the question.
6. **Leave the tree ready for review, not committed.** Per §0.1, you never commit;
   you leave changes in the working tree for the human to inspect and commit.

## 2. Tech Stack & Conventions

- **Language:** TypeScript (strict mode). No `any` unless justified with a comment;
  prefer precise types and `unknown` + narrowing over `any`.
- **Runtime:** Node.js (LTS). ES modules.
- **Package manager:** use the one already configured in the repo; do not switch.
- **Monorepo:** packages live under `packages/`. Respect package boundaries — the
  SDK core stays framework-agnostic and transport-agnostic; framework code lives
  only in adapters, destination code only in transports.
- **Async context:** request context propagation uses `AsyncLocalStorage`. Don't
  thread context manually through function signatures when ALS is the mechanism.
- **Console output:** write to `process.stdout` / `process.stderr` directly, not
  `console.log` (control and throughput; errors/critical to stderr).
- **Queue module only — Messaging:** RabbitMQ via `amqp-connection-manager`; follow
  the RabbitMQ + Worker doc topology exactly.
- **Queue module only — Database:** TimescaleDB (PostgreSQL). Parameterized queries
  only — never string-concatenate SQL. Respect the schema and constraints.

## 3. Reuse Before You Write (DRY)

**Search before creating.** Before writing any type, interface, enum, constant,
validation schema, or utility function, check whether one already exists. Agents
commonly duplicate things that are already defined elsewhere — do not do this.

- **Shared types live in one place.** The `AuditEvent` shape and the `event_type` /
  `severity` / `outcome` / `actor_type` enums are defined **once** in
  `@tnet06/mapa-audit-types` and imported everywhere else (SDK core, adapters,
  transports, Worker). Never redeclare or copy-paste these into another package. A
  divergence between the SDK and the Worker's view of the event shape is a
  correctness bug (it can silently break validation or idempotency).
- **The shared types package is the single source of truth for the event contract.**
  If you need a field that doesn't exist there yet, add it *there* (and flag it),
  don't invent a local variant.
- **Reuse existing utilities.** Serialization, UUID generation, config parsing, the
  `flatten()` helper — if a helper exists, use it. Don't write a second one.
- **If you find near-duplicate code that already exists**, prefer extending or
  importing it over adding a parallel copy. If reconciling them requires a design
  decision, flag it rather than silently forking.
- **Constants and enums are not magic strings.** Don't hardcode `'business'` or
  `'failure'` inline when a shared enum/const defines them.

Rule of thumb: **if two places need the same knowledge, that knowledge lives in one
place and is imported.** Duplication of the event contract is treated as a bug, not
a style preference.

## 4. Code Quality Requirements

- **Match existing style.** Before writing, look at neighboring files and mirror
  their patterns, naming, and structure. Consistency beats personal preference.
- **Error handling is explicit.** No swallowed errors. In the SDK specifically,
  errors must be contained so they never propagate into the host app (the
  fire-and-forget contract), but they must still be surfaced somewhere sensible.
- **No premature abstraction.** Implement what the task needs. Don't build generic
  frameworks or configuration systems that weren't asked for.
- **Comments explain *why*, not *what*.** Especially anything tied to a fixed
  contract (e.g. "id generated here so the queue transport can dedupe — see
  AGENTS.md §0.2").
- **Keep functions small and single-purpose.** In transports, adapters, and (later)
  the Worker loop, keep distinct concerns in separate, testable units.

---

## 5. Testing

- **Write tests for what you implement.** New logic ships with unit tests.
- **Context isolation must be tested** — two concurrent request contexts must never
  mix (a core correctness property of the AsyncLocalStorage design).
- **Fire-and-forget must be tested** — a throwing transport must never propagate to
  the caller.
- **Queue module only:** idempotency and failure paths (redelivery produces no
  duplicate, malformed message → permanent failure, transient failure → retry) are
  core correctness properties, not edge cases.
- **Don't test the framework; test your logic.** Mock transports, RabbitMQ, and the
  DB at the boundaries; assert on your handling, not on library internals.
- **Run the existing test suite** and ensure it passes before considering a task
  done. If you can't run it, say so explicitly.

---

## 6. Security & Data Handling

- The platform captures **PII** (`ip_address`, `user_id`, `user_agent`). Treat
  event data as sensitive: never log full event payloads at `info` level, never
  write PII to stdout in a way that would leak into aggregated logs.
- (Queue module) Validate and sanitize all external input at the Worker boundary
  before it touches the database.
- (Queue module) Never introduce a code path that lets a consuming service write to
  the database directly or bypass the queue.

---

## 7. When You're Unsure

Default order of action when a task is ambiguous:

1. Check the relevant `docs/` design document and the current `BUILD_PLAN.md` phase.
2. Check neighboring code for an established pattern.
3. If still ambiguous **and** it's a low-stakes detail → pick the conventional
   option, implement, and note the assumption.
4. If still ambiguous **and** it touches a contract in §0.2 or any architectural
   decision → **stop and ask the architect.** Do not proceed.

Implementing the wrong thing confidently is worse than asking. The human is the
architect; you are the implementer. Respect that boundary and the collaboration
works well.
